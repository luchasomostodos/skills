# Estructura del README

Cada README de Lucha sigue este orden. Si una parte no aplica, se omite; no se cambia el orden. El modelo es el README de [Coco](https://github.com/luchasomostodos/coco), escrito aquí en lenguaje simple.

## 1. Encabezado

Centrado, con cuatro elementos:

- El nombre del proyecto como título.
- Una frase que diga para qué sirve, en menos de quince palabras.
- Dos líneas que expliquen qué hace hoy y qué viene después.
- Las herramientas que usa, en una sola línea.

```html
<div align="center">

# Nombre del proyecto

### Para qué sirve, en una frase.

Qué hace hoy, en una o dos frases.<br>
Qué viene después, en una frase.

`Herramienta uno` · `Herramienta dos` · `Herramienta tres`

</div>
```

## 2. Estado actual

Tabla de dos columnas, `Ámbito` y `Situación`, con tres o cuatro filas: por ejemplo la prueba piloto, lo que ya funciona, la conversación y la operación diaria. Cada fila dice en una frase cómo está, con uno de los tres estados: funciona, en prueba o falta.

Después de la tabla, un párrafo corto que aclare el límite: que algo esté publicado no significa que se haya probado con casos reales.

## 3. Qué hace hoy

Una lista por cada tipo de persona que usa el proyecto, con el título "Para" y quien sea: `### Para el coach`, `### Para el equipo`. Cada lista tiene de dos a cuatro puntos, en frases que empiezan con un verbo: "Consulta", "Avisa", "Prepara".

Si hay tareas internas que mantienen el proyecto funcionando, van en un grupo aparte, por ejemplo `### Para Tech y Operaciones`.

## 4. Cómo funciona paso a paso

Lista numerada con el recorrido de un caso típico, de principio a fin. Entre tres y cinco pasos. Cada paso dice qué pasa y quién lo nota. Sin nombres de procesos internos: se describe lo que logran.

## 5. Qué falta

Lista de lo que todavía no funciona de punta a punta, cada punto con una frase. Es la parte más útil para quien decide qué sigue, así que se escribe sin suavizar.

## 6. Próximos pasos

Lista numerada, en orden de prioridad, de lo que sigue. Se cierra con una frase que aclare que el orden no asigna responsables ni fechas nuevas, si es el caso.

## 7. Reglas básicas

Uno o dos párrafos con lo que el proyecto cuida siempre. Por ejemplo, quién puede ver qué, qué información no se guarda y cómo habla el proyecto con las personas.

## 8. Documentación

Lista de enlaces a los documentos técnicos y la guía para quien desarrolla, cada uno con una frase que diga qué contiene. Aquí, y solo aquí, pueden aparecer los comandos, o mejor, un enlace al documento donde están.

## 9. Pie

Una línea después de una raya horizontal: fecha de revisión, qué se revisó y qué no. Ejemplo: "Revisado el 5 de noviembre de 2026 contra los flujos publicados. No se comprobó la entrega de mensajes."
